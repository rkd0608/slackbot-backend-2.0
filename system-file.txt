 Complete Application Flow - Detailed Explanation

  Architecture Overview

  Your Slack AI bot is a RAG (Retrieval-Augmented Generation) system that ingests Slack messages and files, stores them with embeddings, and answers questions using retrieved
  context. Here's how everything works:

  ---
  1. Core Components

  FastAPI Application (Port 8000)

  - Receives webhooks from Slack Events API
  - Handles slash commands and interactive components
  - Validates Slack signatures for security
  - Acts as the entry point for all Slack events

  RabbitMQ Message Queues

  Three queues for async processing:
  - slack.events: Raw Slack events (messages, reactions, files)
  - slack.processing: File downloads, channel sync, user sync
  - slack.embeddings: Embedding generation tasks

  Workers (Background Processors)

  Two consumer processes running continuously:
  - Event Consumer: Processes Slack events from the events queue
  - Embedding Consumer: Generates and stores vector embeddings
  - Both run in the same container but handle different queues

  Data Stores

  - MySQL: Persistent storage for messages, files, users, channels, threads
  - Pinecone: Vector database for semantic search (stores embeddings)
  - Redis: Caching layer for API responses and temporary data
  - S3: File storage (currently not configured, would store original files and extracted text)

  ---
  2. Message Ingestion Flow (Step by Step)

  Step 1: Slack Event Occurs

  When a user posts a message in Slack:
  - Slack's Events API sends a webhook POST to https://your-domain/slack/events
  - The webhook contains full event data including message text, user info, channel, timestamp, files, etc.

  Step 2: FastAPI Receives Event

  - app/api/events.py receives the webhook
  - Validates the Slack signature to ensure it's really from Slack (security)
  - Handles the URL verification challenge (one-time setup)
  - Publishes the event to RabbitMQ slack.events queue
  - Returns 200 OK immediately to Slack (within 3 seconds requirement)

  Why use a queue? Because processing can take time (embedding generation, database writes), but Slack requires a response within 3 seconds. The queue allows async processing.

  Step 3: Event Consumer Picks Up Event

  - app/workers/event_consumer.py continuously listens to the events queue
  - When a message arrives, it routes based on event type:
    - message → processes new messages
    - app_mention → bot was mentioned
    - message_changed → message was edited
    - file_shared → file uploaded (though we now handle this differently)
    - reaction_added → emoji reaction added
    - channel_created → new channel created
    - member_joined_channel → user joined a channel

  Step 4: Message Processing

  services/message_processor.py does the heavy lifting:

  Extracts metadata:
  - Message ID (timestamp like 1759639832.861819)
  - Channel ID and name
  - User ID and name
  - Thread info (is this a thread parent or reply?)
  - Timestamp (converted to datetime)

  Analyzes content:
  - Code detection: Scans for code blocks (python, javascript, etc.)
    - Sets has_code = true
    - Extracts code_languages = ['python', 'javascript']
  - Link extraction: Finds URLs in message
    - Stores in links JSON array
    - Sets has_links = true
  - Entity extraction: Identifies people, channels, terms
    - Stores in entities JSON field
  - Importance scoring: Calculates a score based on:
    - Length (longer = more substantial)
    - Has code blocks (+points)
    - In a thread (+points)
    - Has reactions (added later)
    - Formula combines these factors into 0-10 score

  Stores in database:
  - Inserts into messages table with all extracted data
  - Stores raw Slack JSON in raw_json field (for later reference)
  - Links to channel, user, thread if applicable

  Publishes for embedding:
  - Sends message to slack.embeddings queue with message_id
  - This triggers the next step (embedding generation)

  Step 5: File Detection (NEW - What We Fixed Today)

  If the message event contains files:
  - event_consumer.py checks event.get("files", [])
  - For each file in the array:
    - Extracts complete file metadata including url_private (the Slack download URL)
    - Publishes to slack.processing queue with:
        - type: "file_processing"
      - file_info: complete file object from Slack
      - channel_id, user_id, team_id, message_id

  Key insight we discovered: The file_shared event has minimal data, but the message event with subtype: "file_share" has the complete file info including the download URL.
  That's why we now process files from message events.

  Step 6: File Processing

  services/file_processor.py handles file downloads and extraction:

  Check if already processed:
  - Queries database for existing file with same file_id
  - If already processed (is_processed = 1), skip it
  - If exists but not processed, update it with new data

  Create/update file record:
  - Stores metadata: filename, filetype (html, pdf, py, etc.), size, mimetype
  - Crucially stores slack_url (the url_private from file_info) - this was missing before!
  - Links to channel, user, and message

  Download from Slack:
  - Uses slack_client_manager.download_file(slack_url)
  - Authenticates with bot token
  - Gets raw bytes of file content
  - This was failing before because slack_url was NULL

  Upload to S3 (if configured):
  - Stores original file at files/{file_id}/original
  - In your case, S3 isn't configured, so this step is skipped
  - But the code is there for when you add AWS credentials

  Text Extraction (based on filetype):

  The processor has different strategies for different file types:

  - TEXT_EXTRACTABLE (text, python, javascript, java, go, rust, markdown, json, xml, yaml, csv, sql, html):
    - Simply decodes bytes as UTF-8: file_data.decode('utf-8')
    - This gets the raw text content
  - PDF_TYPES (pdf):
    - Uses pypdf library
    - Extracts text from each page
    - Combines with page markers: [Page 1] text [Page 2] text
  - IMAGE_TYPES (png, jpg, gif):
    - Currently skipped (OCR planned for future)
    - Just logs that it detected an image
  - DOC_TYPES (doc, docx):
    - Currently skipped (not implemented yet)

  Today's fix: We added 'html' to TEXT_EXTRACTABLE so HTML files get their text extracted.

  Store extracted text:
  - First 10,000 characters stored in database extracted_text field (for quick access)
  - Full text would go to S3 at files/{file_id}/extracted_text (if S3 configured)
  - Sets s3_text_key field (even though S3 upload fails, the key is set for future use)

  Queue for embedding:
  - Publishes to slack.embeddings queue:
  {
    "type": "file",
    "file_id": "F09K60YKD3K",
    "text": "<full extracted text>",
    "channel_id": "C09JWJ6MP6Y"
  }

  Mark as processed:
  - Sets is_processed = 1
  - Clears processing_error if it was set from a previous failure

  Step 7: Embedding Generation

  workers/embedding_consumer.py handles both message and file embeddings:

  For Messages (type: "message"):
  - Fetches full message from database
  - Builds rich context string:
  Message from @username in #channel
  Timestamp: 2025-10-05
  [if has code] Contains code: python, javascript
  Message: <actual text>
  - Sends to OpenAI embeddings API (text-embedding-ada-002)
  - Gets back 1536-dimensional vector
  - Creates unique vector ID (UUID)
  - Stores in Pinecone with metadata:
    - type: "message"
    - message_id, channel_id, channel_name
    - user_id, user_name
    - timestamp, has_code, importance_score
    - text: first 500 chars (for display in results)
  - Updates database: message.vector_id = <UUID>

  For Files (type: "file"):
  - Fetches file record from database
  - NEW: Fetches channel name from channels table (today's fix)
  - Builds context including channel:
  File: generated-page-2.html
  Title: Finance Dashboard
  Channel: #engineering
  Content: <html>...</html>
  - Generates embedding of this combined context
  - Stores in Pinecone with metadata:
    - type: "file"
    - file_id, filename, filetype
    - channel_id, channel_name ← This is key for filtering!
    - user_id, timestamp
    - text: first 1000 chars of content
  - Updates database: file.vector_id = <UUID>

  Why include channel in the embedding context? Because when someone asks "html file in #engineering", the embedding of the question will be similar to the embedding of "File in
   #engineering" in the file's context. This improves semantic matching.

  ---
  3. Bot Interaction Flow (Answering Questions)

  Step 1: User Asks Question

  Two ways to trigger the bot:
  1. Direct mention: "@RenoBotDev what's in the HTML file in #engineering?"
  2. Direct message: User DMs the bot

  Slack sends either:
  - app_mention event (for @mentions)
  - message event with channel_type: "im" (for DMs)

  Step 2: Event Routing

  event_consumer.py routes to bot interaction:
  - For app_mention: First processes and stores the message (so the bot's response can reference it), then calls bot service
  - For DM: Directly calls bot service (doesn't store user's DM as a regular message)

  Calls bot_interaction_service.handle_message_event(event, db)

  Step 3: Query Analysis

  services/query_analyzer.py uses GPT-4 to understand the question:

  Sends to OpenAI with a structured prompt:
  Analyze this Slack question:
  "what's in the HTML file shared in #engineering"

  Extract:
  1. Query type: factual/summary/code/troubleshooting
  2. Entities: people, projects, technologies
  3. Channels: #engineering → ["engineering"]
  4. Users: @john → ["john"]
  5. Temporal: "last week" → parse dates
  6. Code intent: are they looking for code?
  7. Keywords: important terms

  Returns structured JSON:
  {
    "query_type": "factual",
    "channels": ["engineering"],
    "entities": [
      {"text": "HTML file", "type": "object"}
    ],
    "temporal": null,
    "has_code_intent": false,
    "keywords": ["HTML", "file", "content"]
  }

  Step 4: Query Rewriting

  services/query_rewriter.py handles context resolution:

  Why? Because Slack conversations have context:
  - User: "What did John say about the deployment?"
  - Bot: "John mentioned the deployment was delayed..."
  - User: "When was that?"  ← Needs rewriting!

  The rewriter:
  1. Fetches recent conversation history (last 5 messages between user and bot)
  2. Sends to GPT-4:
  History:
  User: what's the HTML file?
  Bot: I found 2 HTML files...
  User: what's IN it?  ← Current query

  Rewrite this as a standalone query.
  3. Gets back: "What is the content of the HTML file in #engineering?"

  This standalone query is then used for retrieval.

  Step 5: Multi-Stage Retrieval

  This is the most complex part! services/retrieval_service.py uses three parallel retrieval strategies then combines them.

  Strategy 1: Semantic Search (Pinecone)

  Build metadata filters:
  - From query analysis, we know user mentioned "#engineering"
  - Look up channel name "engineering" in MySQL channels table
  - Find channel_id = "C09JWJ6MP6Y"
  - Build Pinecone filter: {"channel_id": {"$in": ["C09JWJ6MP6Y"]}}
  - If query mentioned "last week", add temporal filter: {"timestamp": {"$gte": "2025-09-28"}}
  - If looking for code, add: {"has_code": true}

  Generate query embedding:
  - First, rewrite query to remove conversational fluff:
    - "can you tell me what's in the HTML file?" → "HTML file content engineering"
  - Send cleaned query to OpenAI embeddings
  - Get 1536-dim vector

  Query Pinecone:
  vector_db_manager.query(
      vector=query_embedding,
      top_k=100,
      filter_dict={"channel_id": {"$in": ["C09JWJ6MP6Y"]}},
      include_metadata=True
  )

  Returns: Up to 100 results ranked by cosine similarity
  - Each result has a score (0-1, higher = more similar)
  - Includes the metadata we stored (message_id, channel, user, text preview)

  Why this works for files: Because the file was embedded with "Channel: #engineering" in its context, AND has channel_name: "engineering" in metadata, it matches both
  semantically and via the filter!

  Strategy 2: Keyword Search (MySQL)

  Traditional SQL search:
  SELECT * FROM messages
  WHERE text ILIKE '%HTML%'
    AND text ILIKE '%file%'
    AND channel_name = 'engineering'
  ORDER BY importance_score DESC
  LIMIT 50

  Also applies:
  - User filters (if query mentioned "@john")
  - Temporal filters (date ranges)
  - Code filter (if looking for code snippets)

  Returns: Up to 50 messages that contain the keywords

  Strategy 3: Entity Search (MySQL)

  Uses extracted entities from query analysis:
  - Entities: ["HTML file"]
  - Search for messages containing "HTML file"
  - Score based on how many entities match
  - Order by match count + importance

  Returns: Up to 30 messages with entity matches

  All three run in parallel using asyncio.gather() for speed!

  Step 6: Reciprocal Rank Fusion (RRF)

  Now we have 3 lists of results from different sources. How do we combine them?

  RRF Algorithm:
  For each result at rank position i in a list, assign score:
  score = 1 / (k + i + 1)
  where k = 60 (constant)

  Example:
  - Semantic search returned file F09K60YKD3K at position 0 → score = 1/(60+0+1) = 0.0164
  - Keyword search returned same file at position 5 → score = 1/(60+5+1) = 0.0152
  - Combined score for this file = 0.0164 + 0.0152 = 0.0316

  Messages that appear in multiple lists get higher combined scores!

  The results are sorted by combined RRF score, and top 50 are kept.

  Step 7: Reranking (Optional)

  If we have more than 50 results, we do a second-pass reranking with more sophisticated scoring:

  Feature-based scoring:
  final_score = (
      rrf_score * 0.4 +           # How well it matched retrieval
      importance * 0.2 +           # Message importance (0-1)
      recency * 0.15 +             # How recent (exponential decay)
      reactions * 0.1 +            # Normalized reaction count
      has_code * 0.1 +             # 1.0 if has code, 0 otherwise
      source_diversity * 0.05      # Appeared in multiple sources?
  )

  Recency calculation:
  age_days = (today - message_timestamp).days
  recency = e^(-age_days / 30)
  This means messages from 30 days ago get ~37% of the score of today's messages.

  After reranking, we take the top K (usually 50) for context building.

  Step 8: Context Building

  services/context_service.py takes the message IDs and builds rich context:

  For each retrieved result:

  1. Fetch full message from database
    - Get complete text (not just the preview)
    - Get all metadata
  2. Handle threads
    - If message is in a thread, fetch parent + all replies
    - This gives full conversation context
    - Format as:
    Thread started by @alice:
  "We need to update the dashboard"

  Reply from @bob:
  "I can work on that"

  [Current message]
  3. Handle files
    - If message has file_ids, fetch those files from database
    - Get the extracted_text (up to 10,000 chars)
    - Include in context:
    Attached file: generated-page-2.html
  Content:
  <html>...</html>
  4. Format with metadata
  Message #1 [Score: 0.85]
  From: @rkshtdwivedi8 in #engineering
  Time: 2025-10-05 04:30 PM

  let me know if you can view it

  Attached file: generated-page-2.html
  Content: <html lang="en">
  <head>
      <meta charset="utf-8">
      <title>Finance Visibility Dashboard</title>
  ...

  Build final context document:
  - Sections for different types of content
  - Most relevant messages first
  - Includes file contents inline
  - Truncates if too long (to fit in GPT-4 context window)

  Step 9: Response Generation

  services/bot_interaction.py calls GPT-4:

  System prompt:
  You are Reno, a helpful Slack AI assistant.
  Answer questions based ONLY on the provided context.
  If the context doesn't contain the answer, say so.
  Use citations like [^1] to reference sources.
  Be concise and helpful.

  User prompt:
  Question: what's in the HTML file in #engineering?

  Context:
  [All the formatted context from step 8]

  Answer the question using the context above.

  GPT-4 generates response using the retrieved context.

  Step 10: Response Formatting

  services/response_formatter.py cleans up the response:

  Adds citations:
  - Parses references in the response
  - Adds footnotes:
  The HTML file contains a finance dashboard.

  Sources:
  [^1] Message from @rkshtdwivedi8 in #engineering (2025-10-05)

  Formats for Slack:
  - Converts markdown to Slack's format
  - Wraps code blocks properly
  - Adds emoji if appropriate

  Posts to Slack:
  - Uses slack_client.chat_postMessage()
  - Posts in the same channel/thread where user asked
  - Or in DM if user asked via DM

  4. Why Files Weren't Being Found (What We Fixed)

  Let's trace through what was broken and how we fixed it:

  The Problem:

  User asks: "what's in the HTML file in #engineering?"

  What should happen:
  1. Query analysis extracts channels: ["engineering"]
  2. Retrieval looks up "engineering" → gets channel_id: C09JWJ6MP6Y
  3. Filters Pinecone by channel_id: C09JWJ6MP6Y
  4. Finds files with matching channel_id
  5. Returns file content

  What was actually happening:
  1. Query analysis extracts channels: ["engineering"] ✓
  2. Retrieval tries to look up "engineering" in channels table → NOT FOUND ✗
  3. Channel filter is empty, so no filter applied
  4. OR: Channel not in table, so filter excludes everything
  5. No results returned

  Root Causes (Multiple Issues):

  Issue 1: Files detected but not downloaded
  - Original code only processed file_shared events
  - These events have minimal data, missing url_private
  - File processor tried to download with slack_url = NULL → failed
  - Fix: Process files from message events which have complete file data

  Issue 2: File records not being updated
  - When reprocessing, existing file records weren't updated
  - Code had: file_record = existing or File(...)
  - This kept the old NULL slack_url
  - Fix: Explicitly update existing record fields with new data from file_info

  Issue 3: HTML files not extracted
  - HTML wasn't in TEXT_EXTRACTABLE set
  - Files downloaded but no text extracted
  - Fix: Added 'html' to TEXT_EXTRACTABLE

  Issue 4: Channel not in database
  - Files were in channel C09JWJ6MP6Y ("engineering")
  - But this channel wasn't synced to channels table
  - Retrieval couldn't map "engineering" → channel_id
  - Fix: Manually inserted channel record

  Issue 5: Messages missing channel_name
  - Messages had channel_id but channel_name = NULL
  - Fix: Updated messages to set channel_name

  Issue 6: File embeddings missing channel_name
  - File metadata in Pinecone had channel_id but not channel_name
  - Couldn't filter by channel effectively
  - Fix: Modified embedding_service.embed_file() to:
    - Look up channel_name from channels table
    - Include in embedding context
    - Add to Pinecone metadata

  5. Current System Capabilities

  What Works:

  ✅ Ingests all Slack messages in real-time
  ✅ Detects and extracts code blocks (40+ languages)
  ✅ Downloads and processes files (text, code, HTML, PDF)
  ✅ Generates embeddings for semantic search
  ✅ Multi-stage retrieval (semantic + keyword + entity)
  ✅ Thread context awareness
  ✅ File content retrieval
  ✅ Channel filtering
  ✅ User mention filtering
  ✅ Temporal queries ("last week", "yesterday")
  ✅ Code-specific searches
  ✅ Citation generation
  ✅ Conversation history and context resolution

  What's Not Configured:

  ⚠️ S3 storage (files are extracted but not stored in S3)
  ⚠️ OCR for images
  ⚠️ Word/Excel document processing

  Data Storage:

  - MySQL: ~50GB limit for extracted text in database
  - Pinecone: Unlimited vectors (free tier: 100k vectors)
  - RabbitMQ: Transient (messages deleted after processing)
  - Redis: Cache only (can be cleared)

  Performance:

  - Message ingestion: <100ms per message
  - File processing: 1-5 seconds depending on size
  - Embedding generation: 500ms-1s per item
  - Query answering: 2-5 seconds total:
    - Retrieval: 500ms-1s
    - Context building: 200-500ms
    - GPT-4 generation: 1-3s

  Scalability:

  - RabbitMQ ensures no events are lost
  - Workers can be scaled horizontally (add more containers)
  - Pinecone scales automatically
  - MySQL can handle millions of messages

  That's the complete flow! Every message, file, and query goes through this sophisticated pipeline to enable intelligent Slack search and question answering.
